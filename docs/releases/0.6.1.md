Pi-Bolt 0.6.1 gives the programs Pi starts on macOS their ASLR back. It runs Pi 1.0.0.

### macOS

- **The commands, servers and editors Pi starts run with ASLR again.** Pi's executable runs with ASLR off for its own code, which its prebuilt heap needs, and macOS passed that on to every process it started: commands of the bash tool, MCP and language servers, a dev server started from Pi. Now a helper started with Pi starts them, through `pi-spawn`, a new file beside `pi-bin` ([ARCHITECTURE.md](../ARCHITECTURE.md#the-macos-arm64-port)).
  - A program gets what it got before: its files, directory, environment, signals, limits, and Pi's process group (so it can use the terminal), or a session of its own.
  - `child.pid` is the program's own pid, and signals go to it.
  - Pi waits for `pi-spawn`, which exits as the program did.
  - Not covered: programs started on a pseudo-terminal (Bun's `terminal` option), and Pi's executable started directly, without the `pi` launcher. Those programs are still started without ASLR, as before.
- What it costs:
  - 0.3 ms more at each start (not for `pi --version`);
  - 1.4 ms more for each program Pi starts.
- `PIBOLT_SPAWN_ASLR=0` turns it off. Programs are then started as in 0.6.0: directly, without ASLR, at the same speed as before.

### Tested

- A new test starts programs from an extension. It checks that they have ASLR, along with:
  - exit codes and signals;
  - `ENOENT` and `EACCES`;
  - stdin, stdout, stderr and a fourth descriptor;
  - the working directory and the environment;
  - the pid, `kill()` and timeouts;
  - the process group;
  - a detached shell killed with its children as a group, as Pi's bash tool does.
- The same test with `PIBOLT_SPAWN_ASLR=0`, where the programs must run without ASLR.
- An editor started with Ctrl+G reads the terminal.
