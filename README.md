# Fork tooling for JangMan-J/pi

This branch (`fork-sync`) holds the scripts that keep the fork's integration branch `next`
in sync with `earendil-works/pi`. It lives on its own branch so it survives re-clones; the
earlier copy was untracked and was lost with its working directory on 2026-10-24.

## Set up in a fresh clone

```sh
git remote add upstream https://github.com/earendil-works/pi.git
git fetch origin fork-sync
git worktree add .fork fork-sync
echo .fork >> .git/info/exclude
```

## Install scripts

`install-next.sh` installs `pi` from `next` as a tested release; it needs no checkout. It fetches the
current `origin/next` commit into `~/.local/share/pi-fork/releases/<commit>/`, installs dependencies,
generates the model data, builds, and runs `check.sh focused` from `fork-sync`. Only when the checks pass
does it switch the `current` link to the new release, so `~/.local/bin/pi` (which links through
`current`) changes in one step and running sessions keep their files. A failed build is kept for
inspection and `pi` stays as it was. The previous release stays for `install-next.sh --rollback`; older
ones are deleted. `--reinstall` rebuilds the current commit; `PI_INSTALL_ROOT`, `PI_REPO`, `PI_BRANCH`,
`PI_BIN_DIR` override the defaults. On a fresh machine:

```sh
curl -fsSLO https://raw.githubusercontent.com/JangMan-J/pi/fork-sync/install-next.sh
chmod +x install-next.sh
./install-next.sh
```

`install-tests.sh` sets up a development checkout for changing the fork: it clones `~/pi` if missing
(`PI_DIR` overrides), installs dependencies and the pre-commit hook, builds, builds the pi-env daemon,
sets up this worktree at `.fork/`, aligns the branches with origin, and runs `check.sh focused`
(`--all` for the full suite, `--no-run` for setup only). It does not install `pi`.

## One-click sync (GitHub Actions)

`.github/workflows/fork-sync.yml` runs the full `sync.sh` on demand: Actions tab, "Sync fork and rebuild
next", Run workflow (or `gh workflow run fork-sync.yml -R JangMan-J/pi --ref fork-sync`). Untick "push" for a
dry run. It fast-forwards `main` from upstream, rebases every branch, rebuilds `next`, runs the focused checks
and pushes with `--force-with-lease`. Commits and tags are signed by the `fork-sync bot` key (repo secret
`FORK_SYNC_GPG_KEY`; its public half is on the JangMan-J account, so they show as Verified). On a rebase
conflict it fails without pushing; resolve locally and run `.fork/sync.sh --offline --push`. This branch is the
repository default so the workflow can be dispatched; `main` stays a pure mirror.

## Agents

`AGENTS.md` in this directory is the procedure for anyone (human or agent) changing the fork: branch
ownership, the fixed order of operations, and recovery. `install-tests.sh` writes a `CLAUDE.local.md`
pointer into the checkout and a guarded block into `~/.pi/agent/AGENTS.md` so Claude Code and pi find it.
Start every session with `.fork/sync.sh --status`.

## Files

- `AGENTS.md`: the fork workflow for agents.
- `install-next.sh`: install tested releases of `next`; `install-tests.sh`: set up a development checkout. See above.
- `branches`: the feature branches merged into `next`, in merge order.
- `sync.sh`: `--status` reports main, every branch and next; `--align` resets them to origin when safe; `--rebuild-only` regenerates `next` from the
  current tips; the full mode tags tips, fast-forwards `main`, rebases every branch, rebuilds `next`, runs the
  focused checks and optionally pushes with `--force-with-lease`. It refuses to rebuild over commits made on `next`.
- `check.sh`: `focused` runs the provider payload tests the fork owns; `all` runs `npm run check`
  and `./test.sh`.

## Rules

- Never commit directly to `next`; it is regenerated by `sync.sh`.
- Each fix lives on its owning branch (see `branches`); `next` is only merges.
- Pre-sync tags are signed and pushed, so any previous state is recoverable from GitHub.
